# Руководство по реализации функции Area в Avrora

## Введение

**Area** (Область) — это ключевая функция платформы Avrora, которая превращает простой чат-бот в коллаборативное пространство для работы с знаниями. Это как "рабочая область" или "проект", внутри которого команды могут общаться с AI, делиться документами и управлять контекстом.

### Главная идея

Представьте Area как **умную папку проекта**, которая:
- Хранит историю всех разговоров с AI по конкретной теме
- Помнит контекст и накопленные знания
- Позволяет нескольким людям работать вместе
- Может "форкаться" и "мержиться" как Git-репозиторий
- Управляется через роли и права доступа

## Архитектура системы: три уровня

### Уровень 1: Персональные чаты (уже есть)
- Обычный чат один-на-один с AI
- Приватный, только для владельца
- Используется для быстрых вопросов

### Уровень 2: Area (новый функционал)
- Контейнер для групповых чатов и документов
- Имеет участников с разными ролями
- Накапливает знания по конкретной теме
- Может иметь настройки видимости

### Уровень 3: Групповые чаты внутри Area
- Несколько человек + AI в одном чате
- AI отвечает только когда его упоминают через @avrora
- Все участники видят историю сообщений
- Каждое сообщение имеет автора

## Как это работает: пошаговое описание

### 1. Создание Area

**Что происходит:**
- Пользователь создаёт новую Area с названием и описанием
- Автоматически становится владельцем (owner)
- Выбирает режим видимости: приватная, публичная или DAO-управляемая
- Area получает уникальный ID

**Пример использования:**
```
Пользователь: "Создать Area 'Разработка мобильного приложения'"
Система: Создаёт Area с ID, добавляет пользователя как owner
```

### 2. Система ролей

**Четыре роли в Area:**

- **Owner (Владелец)** - полный контроль
  - Может удалить Area
  - Может назначать администраторов
  - Может менять настройки видимости

- **Admin (Администратор)** - управление контентом
  - Может добавлять/удалять участников
  - Может создавать чаты и документы
  - Может редактировать настройки Area

- **Member (Участник)** - активная работа
  - Может создавать и читать чаты
  - Может добавлять документы
  - Может общаться с AI

- **Viewer (Наблюдатель)** - только чтение
  - Может просматривать чаты
  - Может читать документы
  - Не может писать сообщения

### 3. Групповые чаты с @avrora

**Ключевая механика:**

В обычном чате AI отвечает на каждое сообщение. В групповом чате AI "слушает" разговор и отвечает только когда его позовут.

**Алгоритм работы:**

1. Пользователь пишет сообщение в групповой чат
2. Система проверяет: есть ли в тексте "@avrora"?
3. **Если НЕТ @avrora:**
   - Сообщение просто сохраняется в базу
   - AI ничего не делает
   - Другие участники видят сообщение
4. **Если ЕСТЬ @avrora:**
   - Система берёт последние 20 сообщений как контекст
   - Отправляет их AI вместе с новым сообщением
   - AI генерирует ответ
   - Ответ сохраняется и виден всем

**Зачем ограничение в 20 сообщений:**
- Экономия токенов (= денег)
- Фокус на актуальном контексте
- Предотвращение "размытия" внимания AI

**Пример диалога:**
```
Алиса: "Мне нужно добавить авторизацию"
Боб: "Согласен, давай через OAuth"
Система: [сохраняет, AI молчит]

Алиса: "@avrora помоги написать код для OAuth"
Система: [берёт последние 20 сообщений, включая диалог выше]
AI: "Вот пример реализации OAuth..."
```

### 4. Парсинг упоминаний (mentions)

**Как работает детекция @avrora:**

Система использует регулярные выражения для поиска паттернов:
- `/@avrora/i` - латиница, игнорируя регистр
- `/@аврора/i` - кириллица

**Процесс парсинга:**
1. Берётся текст сообщения
2. Применяется regex поиск
3. Для каждого совпадения:
   - Запоминается позиция в тексте (start, end)
   - Определяется тип упоминания (user или avrora)
   - Сохраняется username

**Дополнительные функции парсера:**
- Может извлекать упоминания пользователей @username (для будущего функционала)
- Может удалять упоминания из текста (для анализа намерения)
- Может разбивать текст на сегменты для UI (обычный текст + упоминания)

### 5. Контекстное управление

**Проблема:** AI имеет ограничение на размер контекста (например, 128K токенов)

**Решение через стратегии:**

**Стратегия 1: Скользящее окно (уже реализовано)**
- Берём последние N сообщений
- Для групповых чатов: N = 20
- Простая и быстрая стратегия

**Стратегия 2: Иерархическое сжатие (будущее)**
- Старые сообщения сжимаются в саммари
- Недавние сообщения сохраняются полностью
- AI получает: [краткий саммари] + [последние 20 сообщений]

**Стратегия 3: RAG (Retrieval-Augmented Generation, будущее)**
- Все сообщения индексируются в векторную базу
- При новом вопросе ищутся семантически похожие
- AI получает только релевантные части истории

### 6. Fork и Merge механизм

**Концепция:**

Вдохновлено Git. Позволяет создавать "ветки" знаний и объединять их.

**Сценарий использования:**

```
[Area: "Дизайн продукта"]
    ↓ fork (Алиса)
[Area: "Дизайн продукта (Вариант А)"]
    - Алиса экспериментирует с идеями
    - Создаёт свои чаты и документы
    ↓ merge proposal
[Area: "Дизайн продукта"]
    - Владелец ревьюит изменения
    - Принимает или отклоняет
```

**Статусы Area:**
- `independent` - самостоятельная Area, не связана с другими
- `synced` - форк, синхронизирован с родителем
- `diverged` - форк, ушёл в своё направление
- `merge_proposed` - создан запрос на слияние

**Что сохраняется при fork:**
- `parentAreaId` - ссылка на родительскую Area
- `inheritedSummary` - краткое содержание знаний на момент форка
- `forkedAt` - временная метка форка

### 7. Система видимости

**Три режима:**

**Private (Приватная):**
- Видна только участникам
- Нужно явное приглашение
- Используется по умолчанию

**Public (Публичная):**
- Видна всем пользователям платформы
- Можно просматривать без приглашения
- Для участия нужно присоединиться

**DAO (Управление через токены):**
- Доступ на основе владения токенами
- Голосование по важным решениям
- Связь с блокчейном через `daoTokenAddress`

### 8. Документы в Area

**Концепция:**

Area может содержать документы — артефакты работы с AI:
- Код
- Таблицы
- Изображения
- Текстовые заметки

**Связь документов:**
- Документы создаются через AI tools
- Привязываются к Area через таблицу `AreaDocument`
- Могут иметь версии и изменения
- Могут быть базой для RAG поиска

### 9. Merge Proposals (запросы на слияние)

**Процесс:**

1. **Создание предложения:**
   - Пользователь форкнул Area, поработал
   - Хочет внести изменения в оригинал
   - Создаёт `AreaMergeProposal`

2. **Содержание предложения:**
   - `title` - что предлагается
   - `description` - детальное описание
   - `changesSummary` - AI-генерируемый саммари изменений

3. **Ревью:**
   - Владелец оригинальной Area получает уведомление
   - Просматривает изменения
   - Может принять (approved), отклонить (rejected) или оставить открытым (open)

4. **Слияние:**
   - Если approved, статус меняется на `merged`
   - Контент из форкнутой Area переносится в оригинал
   - История сохраняется

## Базы данных: структура и связи

### Главные таблицы:

**Area (Области):**
```
id - уникальный идентификатор
title - название
description - описание
ownerId → User - кто создал
visibility - приватная/публичная/DAO
parentAreaId → Area - родительская область (для fork)
mergeStatus - статус слияния
daoTokenAddress - адрес токена для DAO
```

**AreaMember (Участники области):**
```
areaId → Area
userId → User
role - owner/admin/member/viewer
joinedAt - когда присоединился
```

**Chat (Чаты):**
```
[существующие поля...]
areaId → Area - к какой области относится
chatType - personal/group - тип чата
```

**Message_v2 (Сообщения):**
```
[существующие поля...]
userId → User - кто написал (для групповых чатов)
```

**ChatMember (Участники чата):**
```
chatId → Chat
userId → User
role - admin/member
joinedAt - когда присоединился
lastReadAt - когда последний раз читал
```

**MessageMention (Упоминания):**
```
messageId → Message
mentionedUserId → User - кого упомянули (null для @avrora)
mentionType - user/avrora
mentionText - текст упоминания (@avrora)
```

### Связи между таблицами:

```
User
  ↓ owns
Area
  ↓ contains
Chat (group/personal)
  ↓ has
Message
  ↓ contains
MessageMention

User
  ↓ member of
AreaMember → Area

User
  ↓ member of
ChatMember → Chat
```

## API маршруты: концепция

### Операции с Area:

**GET /api/areas**
- Получить список всех Area пользователя
- Фильтры: по роли, по видимости
- Возвращает: массив объектов Area с ролью пользователя

**POST /api/areas**
- Создать новую Area
- Тело запроса: title, description, visibility
- Автоматически добавляет создателя как owner

**GET /api/areas/[id]**
- Получить конкретную Area
- Проверяет права доступа
- Возвращает: данные Area + список чатов + список участников

**PATCH /api/areas/[id]**
- Обновить Area
- Только для owner/admin
- Можно менять: title, description, visibility

**DELETE /api/areas/[id]**
- Удалить Area
- Только для owner
- Каскадное удаление всех чатов и связей

### Управление участниками:

**GET /api/areas/[id]/members**
- Список участников Area
- Возвращает: userId, role, email, joinedAt

**POST /api/areas/[id]/members**
- Добавить участника
- Только для owner/admin
- Тело: userId, role

**PATCH /api/areas/[id]/members/[userId]**
- Изменить роль участника
- Только для owner

**DELETE /api/areas/[id]/members/[userId]**
- Удалить участника
- Только для owner/admin

### Fork и Merge:

**POST /api/areas/[id]/fork**
- Создать форк Area
- Копирует структуру, но не историю сообщений
- Создаёт саммари родительской Area

**POST /api/areas/[id]/merge-proposals**
- Создать предложение о слиянии
- Тело: targetAreaId, title, description

**PATCH /api/areas/[id]/merge-proposals/[proposalId]**
- Принять/отклонить предложение
- Только для owner целевой Area

## WebSocket: реал-тайм обновления

### Зачем нужен WebSocket:

В групповых чатах несколько людей пишут одновременно. HTTP запросы не подходят — нужны мгновенные обновления.

### Архитектура:

**Клиент (браузер):**
- Подключается к WebSocket серверу
- Отправляет: `{ chatId, areaId, token }`
- Слушает события

**Сервер:**
- Держит соединения открытыми
- При новом сообщении в чате:
  - Находит всех подключённых к этому chatId
  - Отправляет им событие: `{ type: "new_message", data: {...} }`

**События:**
- `new_message` - новое сообщение
- `user_joined` - пользователь вошёл в чат
- `user_left` - пользователь покинул чат
- `typing` - кто-то печатает
- `message_read` - сообщение прочитано

### Технические детали:

**Подключение:**
```
ws://localhost:3001?chatId=xxx&token=yyy
```

**Авторизация:**
- Token проверяется при подключении
- Если невалидный — соединение закрывается

**Переподключение:**
- При обрыве связи клиент автоматически переподключается
- Интервал: 5 секунд между попытками

**Масштабирование:**
- Для продакшена: использовать Redis Pub/Sub
- Множественные WebSocket серверы подписываются на Redis каналы
- События публикуются в канал, все серверы получают

## Продвинутые функции (будущее)

### 1. Мультиагентная архитектура

**Проблема:**
Сейчас все запросы идут в GPT-5 (дорого и медленно для простых вопросов)

**Решение:**
Иерархия агентов:

```
[Пользователь спрашивает]
    ↓
[Лёгкий агент: Gemma 2B / Phi-4 Mini]
    - Классифицирует вопрос
    - Простой вопрос? → отвечает сам
    - Сложный? → передаёт дальше
    ↓
[Супервизор: GPT-4o-mini]
    - Разбивает на подзадачи
    - Координирует ответы
    - Очень сложный? → передаёт дальше
    ↓
[Эксперт: GPT-5]
    - Отвечает на сложнейшие вопросы
    - Генерирует итоговое решение
```

**Выгода:**
- 80% вопросов обрабатывается лёгкими моделями
- Экономия ~10x по цене
- Ускорение ответов в 2-3 раза

### 2. RAG (Retrieval-Augmented Generation)

**Что это:**
Система семантического поиска по истории Area

**Как работает:**

1. **Индексация:**
   - Каждое сообщение превращается в вектор (embedding)
   - Векторы сохраняются в специальную базу (Pinecone, Weaviate)

2. **Поиск:**
   - Новый вопрос → вектор
   - Ищем похожие векторы в базе
   - Достаём топ-10 релевантных сообщений

3. **Генерация:**
   - AI получает: [найденные сообщения] + [новый вопрос]
   - Генерирует ответ на основе контекста

**Пример:**
```
История (1000 сообщений):
- Обсуждение архитектуры базы данных (3 месяца назад)
- Обсуждение UI компонентов (вчера)

Новый вопрос: "Как мы решили хранить пользователей?"
RAG находит: сообщения про архитектуру БД
AI отвечает: "Вы решили использовать PostgreSQL с таблицей User..."
```

### 3. Контекстные саммари

**Проблема:**
История Area растёт → нужно сжимать для экономии токенов

**Решение:**

Периодически (раз в день/неделю) запускается задача:
1. Берёт последние N сообщений
2. Отправляет в AI с промптом: "Сделай краткое саммари"
3. Сохраняет саммари в поле Area
4. При новом запросе: [саммари] + [свежие сообщения] → AI

**Многоуровневое сжатие:**
```
Уровень 1: Последние 20 сообщений (полностью)
Уровень 2: 20-100 сообщений (сжатые саммари)
Уровень 3: 100+ сообщений (общее саммари Area)
```

### 4. DAO управление

**Концепция:**
Важные решения в Area принимаются голосованием

**Механизм:**

1. **Токены:**
   - Area связана с ERC-20 токеном
   - Владельцы токенов = участники DAO

2. **Голосование:**
   - Предложения: добавить участника, изменить настройки, мержить форк
   - Вес голоса = количество токенов
   - Порог принятия: 50%+ токенов

3. **Смарт-контракты:**
   - Хранят правила голосования
   - Автоматически исполняют решения

**Пример:**
```
Предложение: "Сделать Area публичной"
За: 60% токенов
Против: 40%
Результат: Предложение принято, Area стала public
```

## Ключевые моменты для разработчика

### 1. Проверка прав доступа

**Везде проверяем:**
- Может ли пользователь читать Area?
- Может ли пользователь писать в чат?
- Может ли пользователь изменять настройки?

**Логика:**
```
Если Area публичная → все могут читать
Если приватная → только участники
Если groupChat → все участники Area имеют доступ
Если personalChat → только владелец
```

### 2. Оптимизация производительности

**Проблемы:**
- Регулярные выражения в циклах → медленно
- Большие истории чатов → переполнение памяти

**Решения:**
- Компилировать regex один раз (module-level constants)
- Ограничивать контекст (20 сообщений для группы)
- Использовать индексы в БД (areaId, chatId, userId)
- Кешировать список участников

### 3. Безопасность

**Защита от:**
- SQL injection → используем ORM (Drizzle)
- XSS атаки → санитизация HTML в сообщениях
- CSRF → токены в WebSocket соединениях
- Rate limiting → ограничение запросов к AI

### 4. Тестирование

**Что тестировать:**
- Парсинг @avrora с разными вариантами (латиница, кириллица, регистр)
- Права доступа: попытки несанкционированного доступа
- Групповые чаты: AI молчит без mention
- Контекстные лимиты: только 20 сообщений передаются

## Заключение

Area — это не просто "папка с чатами". Это:
- **Пространство знаний** с накопительной памятью
- **Коллаборативный инструмент** для командной работы с AI
- **Версионируемая система** с fork/merge механизмом
- **Масштабируемая платформа** для будущих функций (RAG, мультиагенты, DAO)

Главная магия в том, что AI "помнит" контекст Area и может отвечать на вопросы, учитывая всю предыдущую историю работы команды.

При реализации главное — начать с простого (базовые Area + групповые чаты), протестировать, и постепенно добавлять продвинутые функции.
